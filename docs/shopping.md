# Lista de compras compartida

Milestone 6 adds `/shopping`, available as **Compras** in the shared account navigation. Accounts must be verified and belong to the household. No new external provider, sending domain, or hosting configuration is needed. Restart the development server after pulling this milestone so Mongoose loads the updated ShoppingItem schema.

## Everyday flow

- **Pendientes**: add an inventory product or a custom item. Low-stock copies start at 1. Use the inventory-style minus/number/plus stepper, or type a positive whole quantity directly, then press its check control; the quantity and purchased state save together, without an edit modal or separate Save step. Remove an unwanted item after confirmation.
- **Agregar faltantes**: after confirmation, add active products at zero stock or at/below their warning threshold. Each new entry starts at quantity 1. Existing pending/purchased entries retain their quantities; repeated additions do not duplicate linked products.
- Checking an item moves it to **Comprados** immediately without changing stock. Unchecking returns it to Pending with its saved quantity, where it can be adjusted again. Unsaved quantity drafts retain their original revision and pause background refresh so another member’s edit cannot silently be overwritten.
- In **Comprados**, **Confirmar recepción (N)** receives the whole reviewed purchase in one click. Linked product quantities are added to stock together; custom items become received without creating products or stock movements. The page then opens **Recibidos**. If a quantity needs correcting, return the item to Pending, edit it, and check it again before confirmation.
- **Recibidos** keeps read-only receipt history with actual quantities and Panama timestamps. A later shopping trip can add the same product again as a new item. Receiving completes the item; it does not automatically split a partially fulfilled quantity into a new pending entry.

Purchases reuse shared dialogs, list surfaces, floating creation controls, search filters, typography, and touch targets. Purchased rows expose unchecking/removal; one shared action confirms all saved quantities. Pending rows use the shared QuantityInput and inventory quantity-controls styles. Per the compact-row preference, check, name, stepper, and removal stay in one row on both phones and desktop. Row buttons use the shared 32px compact-control token while quantity entry uses its 44px compact-width token. Names wrap to at most two lines, with controls centered beside the name; default controls elsewhere retain their normal sizes. Minus stops at 1 and plus at the maximum safe whole quantity. Buttons change only the draft, which saves with the purchase check. Names wrap/clamp safely. Search stays in URL parameters; clearing preserves the selected status tab. The product picker initially shows up to 100 active products and can search the whole household inventory by literal name. Shopping views show up to 100 items, with count/limit guidance and name search. Pending/purchased entries are oldest first, while received entries are newest first.

The existing focus/online/30-second refresh behavior is reused for household updates. Purchase controls reconcile confirmed revisions immediately and retain their request/data on uncertain saves. Creation/removal forms reopen the canonical page after a confirmed write. Whole-purchase receipt opens the received-history view. This milestone does not introduce offline writes or push subscriptions.

## Persistence and consistency

`models/ShoppingItem.ts` stores the product link (optional), snapshot name/unit, planned quantity, status, actor, revision, actual received quantity/time, and receipt movement link. Legacy missing revisions read as zero; legacy units fall back to unidades.

`lib/shopping/mutations.ts` reuses the inventory transaction wrapper and quantity-change operation. Current verified sessions and household membership are checked inside every mutation, including deduplicated retries. Household access locks serialize against member removal and concurrent list/inventory changes. Fingerprinted InventoryRequest records retain the original result. Shopping commands have distinct operation names, and IDs cannot be reused with different payloads.

Two members confirming the same purchase cannot add stock twice, even with different request IDs. The receipt selection pins item IDs, revisions, and quantities from the same query that supplies the displayed rows. Receipt includes all reviewed purchased entries beyond the 100-row display limit, but never purchases added after that snapshot. Search-filtered views require returning to the full purchase before receipt. The entire selected set and all stock movements commit in one transaction; one stale item, changed unit, invalid status, or stock overflow rolls everything back. Each linked entry gets a distinct deterministic movement request ID derived from the batch request and item ID. Fingerprinted batch retries return the previous result. Rows are disabled during an uncertain batch, and automatic refresh pauses until it is resolved. Purchase checkboxes have no stock side effect. Stale edits, invalid quantities, stock overflow, missing/archived foreign products, and removed membership fail without partial receipt writes. A changed product unit blocks receipt and asks the user to remove/re-add the item, preventing quantities in an old unit from being applied to a new one. Concurrent quantity changes in the same unit are preserved through atomic stock increments.

A receipt can later be undone through normal inventory activity. The received shopping entry remains historical and cannot be received again; add a new entry if needed. Custom entries deliberately do not create inventory products. Linked names/units are snapshots for the shopping trip, rather than silently changing when inventory metadata changes.

## Verification

`npm run check` covers lint, TypeScript, unit tests, and the production build. `npm run db:check` uses a generated disposable database on the existing local replica, with email mocked. Shopping tests cover buying vs receiving, inline quantity purchase updates, whole-purchase receipt snapshots, replay protection, concurrent receivers, repeated/manual bulk additions, custom items, stale changes, removed members, session verification, household isolation, unit changes, overflow/archived rollback, literal searching, and inventory lookup beyond the initial 100 choices.

Browser review uses a separate MongoDB process on port 27019 and disposable household accounts with email disabled. Checks cover two-account receipt/history, adding/editing/removing, custom receipts, modal search, mobile/desktop layouts, inline number fields, and interrupted purchase/receipt responses that retry with the same request. The user's saved database on port 27018 is kept running. Real household use on both phones remains the user's milestone review.
